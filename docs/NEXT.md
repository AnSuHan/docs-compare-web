### ⚠️ 가장 중요한 한 가지

**실제 문서가 한 번도 파서를 통과한 적이 없다.**

파서 6종은 전부 구현됐고 단위 테스트 150개를 통과하지만, 그 입력은 전부
우리가 손으로 만든 합성 데이터다. 실제 DOCX·HWP·HWPX·PDF 파일이 이 코드를
통과하는 것을 아직 아무도 보지 못했다.

- 지금까지 사람이 확인한 것: 화면이 뜬다, 워커가 돈다, txt/md 경로가 돈다
- 확인되지 않은 것: 실제 한글 공문서에서 텍스트가 제대로 나오는가

기획서가 M3·M4 종료 조건(§6.10, §7.8)을 항목별로 못박아 둔 이유가 이것이다.
**다음 작업의 1번은 코드를 더 쓰는 것이 아니라 실문서를 통과시켜 보는 것이다.**

## 2. 다음에 할 일 (우선순위 순)

### P0-1. 실문서로 파서 검수 — 선행 조건: 픽스처

지금 막혀 있는 유일한 이유는 **테스트할 문서가 없다**는 것이다.

**필요한 것** (기획서 §13.2 를 실무적으로 줄인 최소 세트)

| 종류 | 최소 개수 | 어디서 |
|---|---|---|
| 한글 공문서 `.hwp` | 5 | 정부24, 나라장터 공고문 |
| `.hwpx` | 3 | 같은 문서를 한/글에서 hwpx 로 저장 |
| 공문서 `.pdf` | 5 | 나라장터 공고문 (태그된 것/아닌 것 섞어서) |
| 스캔 `.pdf` | 1 | 인쇄 후 스캔한 것 아무거나 |
| `.docx` | 3 | 표·제목·목록이 있는 것 |
| 같은 원본을 다른 도구로 출력한 PDF 쌍 | 2쌍 | Word 출력 vs 한/글 출력 |

민감하지 않은 공개 문서면 된다. `src/fixtures/private/` 는 `.gitignore` 에
들어 있으므로 개인 문서를 넣어도 커밋되지 않는다.

**검수 방법** — 파일을 `/docdiff/admin` 의 "파일로 확인"에 넣으면
파서·블록 수·신뢰도·경고·추출 트랙·소요 시간이 그대로 나온다. 그 값을 모아
아래 판정을 한다.

- HWP 추출 성공률 **80% 미만이면 v1 에서 `.hwp` 를 뺀다** (기획서 §7.8-8 의 결정)
- 제어문자 잔여가 0 이 아니면 `paraText.ts` 의 8 WCHAR 처리에 구멍이 있다
- PDF 트랙 A 적중률이 높으면 §6.5 기하 재조립 부담이 그만큼 준다
- 정상 한글 PDF 가 `GARBLED_TEXT` 로 잡히면 `hangulSanity.ts` 임계값이 과하다

### P0-2. 골든 테스트 하네스 (T-018, §13.3)

픽스처가 생기면 바로 붙인다. 픽스처 없이 만들면 껍데기만 남는다.

- 각 픽스처의 `NormalizedDoc` 을 JSON 스냅샷으로 저장
- 최상위 회귀 테스트: **자기 자신과 비교하면 변경점 0** (§13.1)
- 의미상 같지만 바이트가 다른 쌍도 넣는다 — 이게 실제 사용 패턴이다
  - 같은 문서를 Word 에서 재저장 / 다른 도구로 PDF 출력
  - UTF-8 과 CP949 로 각각 저장한 텍스트
  - 같은 문서를 HWP 와 HWPX 로 각각 저장
- `parserVersion` 을 올리면 스냅샷을 갱신한다

### P1-1. PDF 정확도 튜닝 (T-034 ~ T-038)

검수 결과가 나온 뒤에 손댈 곳들. **지금 미리 만지면 근거 없이 만지는 것이다.**

- `columnDetect.ts` — 2단 논문에서 읽기 순서가 틀리면 gutter 임계값(3%)과
  `COLUMN_MIN_LINES`(5)를 조정
- `paragraphMerge.ts` — 문단이 과하게 이어붙으면 `LINE_FULL_RATIO`(0.95)를 올리고,
  과하게 끊기면 `PARA_GAP_RATIO`(1.5)를 올린다
- `hangulSanity.ts` — 오탐이 나오면 표본 하한(100음절)과 엔트로피 임계(0.92)를 조정
- `headerFooter.ts` — 머리말이 안 잡히면 `HEADER_REPEAT_RATIO`(0.6)를 낮춘다

### P1-2. 암호 PDF 비밀번호 모달 (T-040)

지금은 `ENCRYPTED` 에러로 끝난다. pdf.js 의 `PasswordException` 을 받아
비밀번호를 물어보고 다시 시도하는 경로가 필요하다. **비밀번호가 서버로 가지
않는다는 문구를 모달에 반드시 적는다.**

### P1-3. E2E (T-073, §13.4)

Playwright 6개 시나리오. 지금은 배포할 때마다 사람이 눌러 보고 있다.

1. TXT 2개 → Unified 비교 → 변경점 점프
2. DOCX 2개 → Split → 옵션 토글 → 결과 갱신
3. PDF 2개 → 진행률 → 취소
4. PDF + DOCX → 뷰어 분할
5. HWPX 1개 → 단일 뷰어
6. 손상 파일 → 에러 화면

### P2-1. 접근성 감사 (T-072)

axe 로 훑는다. 지금 지킨 것: 거터 기호로 색 의존 제거, `role="progressbar"`,
변경 행 `aria-label`, 키보드 접근. 검증은 안 했다.

### P2-2. i18n ko/en (T-066)

## 3. 알려진 한계 (사용자에게 설명해야 하는 것)

기획서 §5.6 과 각 파서의 한계를 합친 것. `/docdiff/admin` 에도 같은 내용이 있다.

- **문단 이동(move)을 감지하지 못한다.** 자리만 바뀐 문단은 삭제+추가로 보인다. v2
- **표는 평탄화된다.** 셀 단위 변경을 짚어주지 못한다
- **서식만 바뀐 변경은 잡지 않는다** (D-03). 볼드 추가 등
- **배포용(열람 제한) HWP 는 열 수 없다.** 감지해서 안내만 한다
- **스캔 PDF 는 비교를 차단한다.** 브라우저 OCR 은 100쪽에서 UX 가 무너진다
- **다단 조판 PDF 의 읽기 순서는 추정이다.** 신뢰도를 0.6 으로 낮춰 표시한다
- `.doc`(구버전 바이너리)는 지원하지 않는다. `.docx` 로 저장 후 재시도 안내

## 4. 운영 메모

### 배포

```bash
npm run verify        # 통과 못 하면 배포하지 않는다
npm run deploy:plan   # 바뀐 파일만 뽑는다
# → 그 목록을 write_file 로 올린다 (새 폴더는 make_dir, 지울 건 delete_file)
# → restart_app
npm run deploy:record
```

자세한 내용과 이 구성에 얽힌 함정 세 가지(마운트 경로, `preview.allowedHosts`,
빌드 도구를 `dependencies` 에 두는 이유)는 `README.md` 의 배포 절 참고.

### 이 프로젝트에서 이미 밟은 지뢰

같은 실수를 반복하지 않도록 남긴다.

1. **워커에는 DOM 이 없다.** 기획서의 `DOMParser`·mammoth 예시를 그대로 쓰면
   배포에서 죽는다. `core/xml.ts` 스캐너를 쓴다
2. **프록시가 `/docdiff` prefix 를 뗀다.** 빌드는 절대경로, 서빙은 루트.
   상대경로로 두면 끝 슬래시 없는 주소에서 자산이 다른 앱으로 새어 나가고,
   서빙까지 절대경로로 두면 무한 리디렉트가 된다
3. **플랫폼은 `vite preview` 로만 띄우고 재빌드해 주지 않는다.**
   `rebuild-if-stale` 플러그인이 그걸 메운다
4. **O(n·m) DP 는 블록 8,000개에서 256MB 를 잡는다.** Myers + 앵커 분할로 바꿨다
