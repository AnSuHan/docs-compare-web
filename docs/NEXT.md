## 2. 다음에 할 일 (우선순위 순)

### P0-1. 실문서로 파서 검수 — 선행 조건: 픽스처

지금 막혀 있는 유일한 이유는 **테스트할 문서가 없다**는 것이다.

**필요한 것** (기획서 §13.2 를 실무적으로 줄인 최소 세트)

| 종류 | 최소 개수 | 어디서 |
|---|---|---|
| 한글 공문서 `.hwp` | 5 | 정부24, 나라장터 공고문 |
| `.hwpx` | 3 | 같은 문서를 한/글에서 hwpx 로 저장 |
| 공문서 `.pdf` | 5 | 나라장터 공고문 (태그된 것/아닌 것 섞어서) |
| 스캔 `.pdf` | 1 | 인쇄 후 스캔한 것 아무거나 |
| `.docx` | 3 | 표·제목·목록이 있는 것 |
| 같은 원본을 다른 도구로 출력한 PDF 쌍 | 2쌍 | Word 출력 vs 한/글 출력 |

민감하지 않은 공개 문서면 된다. `src/fixtures/private/` 는 `.gitignore` 에
들어 있으므로 개인 문서를 넣어도 커밋되지 않는다.

**검수 방법** — 문서를 `src/fixtures/private/` 에 넣고 터미널에서 돌린다.

```bash
npm run inspect                        # private/ 아래 전부
npm run inspect -- 어떤파일.hwp        # 하나만
npm run inspect -- --json snapshots/   # NormalizedDoc 스냅샷까지 저장
```

`scripts/inspect.ts` 는 워커를 거치지 않고 `document.worker.ts` 와 같은 순서로
파서를 직접 부르고(크기 검사 → `resolveFormat` → `loadParser` → `parse`),
파일마다 파서·블록 수·글자 수·신뢰도·경고·추출 트랙·소요 시간과 함께
**아래 판정을 코드로 돌린 결과**(`>` 로 시작하는 줄)를 찍는다. 마지막에
형식별 성공률과 PDF 트랙 분포를 낸다. 파일 하나만 눈으로 볼 때는
`/docdiff/admin` 의 "파일로 확인"도 그대로 쓸 수 있다.

판정 규칙은 이것이다.

- HWP 추출 성공률 **80% 미만이면 v1 에서 `.hwp` 를 뺀다** (기획서 §7.8-8 의 결정)
- 제어문자 잔여가 0 이 아니면 `paraText.ts` 의 8 WCHAR 처리에 구멍이 있다
- PDF 트랙 A 적중률이 높으면 §6.5 기하 재조립 부담이 그만큼 준다
- 정상 한글 PDF 가 `GARBLED_TEXT` 로 잡히면 `hangulSanity.ts` 임계값이 과하다

### P0-2. 골든 테스트 하네스 (T-018, §13.3)

픽스처가 생기면 바로 붙인다. 픽스처 없이 만들면 껍데기만 남는다.

스냅샷을 뽑는 쪽은 이미 있다 — `npm run inspect -- --json <dir>` 가
`NormalizedDoc` 을 파일당 하나씩 저장한다(`parsedAt` 은 매번 달라지므로 뺀다).
남은 것은 그 스냅샷을 고정해 놓고 비교하는 테스트다.

- 각 픽스처의 `NormalizedDoc` 을 JSON 스냅샷으로 저장
- 최상위 회귀 테스트: **자기 자신과 비교하면 변경점 0** (§13.1)
- 의미상 같지만 바이트가 다른 쌍도 넣는다 — 이게 실제 사용 패턴이다
  - 같은 문서를 Word 에서 재저장 / 다른 도구로 PDF 출력
  - UTF-8 과 CP949 로 각각 저장한 텍스트
  - 같은 문서를 HWP 와 HWPX 로 각각 저장
- `parserVersion` 을 올리면 스냅샷을 갱신한다

### ~~P1-3. E2E (T-073, §13.4)~~ ✅

`npm run test:e2e` — Playwright 로 7개 시나리오. 13초쯤 걸린다.

1. TXT 2개 → 비교 → 변경점 점프 (조사 한 글자만 강조되는지까지 본다)
2. DOCX 2개 → 나란히 → 옵션 토글 → 결과 갱신
3. PDF 2개 → 진행률 → 취소
4. PDF + DOCX → 뷰어 분할
5. HWPX 1개 → 단일 뷰어
6. 손상 파일 → 에러 화면
7. 암호 PDF → 비밀번호 모달 → 비교 (T-040)

문서는 `tests/helpers/makeDocs.ts` 가 만든다 — 저장소에 바이너리를 두지 않고,
시나리오가 필요로 하는 만큼(진행률을 보려면 400쪽) 그때 만든다.

**이걸 붙이자마자 버그 두 개가 나왔다.** 둘 다 사람이 눌러 보면서는 못 본 것들이다.

- **워커 경계에서 에러 코드가 사라지고 있었다.** Comlink 는 던져진 Error 를
  message/name/stack 으로만 직렬화한다. AppError 를 그대로 던지니 `code` 가
  없어져 화면은 어떤 실패든 CORRUPTED 로 봤다. 문구가 우연히 같아 여태 안 보였고,
  T-040 의 비밀번호 모달은 실제 앱에서 아예 열리지 않았다.
  → 워커가 `toJSON()` 으로 바꿔 던지고 클라이언트가 되살린다
- **취소한 뒤 진행률이 되살아났다.** 워커를 terminate 해도 이미 큐에 올라온
  진행률 메시지는 배달된다. "중단했습니다" 위에 진행률이 남아 영영 사라지지 않았다.
  → 취소 뒤 도착한 진행률은 버린다

### ~~P2-1. 접근성 감사 (T-072)~~ ✅

axe(WCAG 2.1 AA)를 화면 상태마다 돌린다 — 첫 화면, 비교 결과(한 줄로/나란히),
뷰어 분할, 에러, 비밀번호 모달(틀린 뒤 포함), 단축키 도움말, 진단 화면.
다크 모드도 따로 본다(팔레트가 통째로 다르다). 위반이 하나라도 나오면 실패한다.
axe 가 못 보는 초점 순서는 키보드 시나리오로 따로 확인한다
(Tab → Enter → n/p → s → ? → Esc).

**처음 돌렸을 때 위반 3종이 나왔다.**

- **파일 입력에 이름이 없었다** (critical, 8개 화면 전부). `sr-only` 라 눈에는
  안 보여도 스크린리더에는 남는다. 이름이 없으면 "편집" 으로만 읽혔다
  → `aria-label` 추가 (`이전 문서 고르기` / `이후 문서 고르기`, 진단 화면 포함)
- **`--color-*-strong` 을 글자색으로 쓴 자리들** (serious). 이 토큰은 강조 *배경*
  이라 본문 배경 위에서는 대비가 4.5:1 에 못 미쳤다 (`+3 −1` 요약, 비밀번호
  오류 문구, 진단 화면 체크 표시)
  → `--color-add-text` / `--color-del-text` 를 새로 두고 글자는 그쪽을 쓴다
- **진행률에 이름이 없었다** (serious). `role="progressbar"` 만 있고 라벨이 없어
  무엇의 진행인지 읽어 줄 수 없었다 → `aria-label="처리 진행률"`, `aria-valuemin` 추가

전부 고쳤고 11개 검사가 통과한다.

**그리고 이 검사가 더 큰 것을 하나 더 드러냈다 — 앱이 사실 "다크 전용" 이었다.**

배포본 CSS 를 열어 보니 밝은 값이 아예 없었다(`#f6f7f8` 0번, dark 미디어쿼리 0개).
Tailwind v4 는 `@theme` 블록을 전부 하나의 `:root` 로 끌어올린다. `index.css` 가
미디어쿼리 안에 두 번째 `@theme` 을 두고 있어서 **미디어쿼리가 사라지고 다크 값이
밝은 값을 그냥 덮어썼다.** M0 부터 계속 그랬고, 그래서 위 접근성 검사도 처음에는
"라이트" 라고 이름 붙인 채 전부 다크 화면만 보고 있었다.

- 다크는 `@theme` 이 아니라 평범한 `@media (...) { :root { ... } }` 로 덮어쓴다
- 밝은 팔레트를 처음으로 실제 검사하자 대비 위반이 쏟아졌다 — 원인은 하나,
  `--color-ink-400` (#8b939f) 이 밝은 배경에서 2.9:1 밖에 안 됐다. #646b78 로 내렸다
- 이제 첫 화면 검사가 `body` 배경이 정말 밝은지, 다크 검사가 정말 어두운지를
  각각 먼저 확인한다. 그러지 않으면 같은 화면을 두 번 보는 셈이다

### P2-0. 세 칸 보기의 가운데 편집 (다음 차례)

세 칸 보기(왼쪽만 / 공통 / 오른쪽만)는 붙였다. 남은 것은 **가운데를 직접 고쳐
합의된 문서를 만드는 것** 이다. 지금 구조가 그걸 전제로 잡혀 있다.

- 조각은 `components/diff/tripleRows.ts` 의 순수 함수가 만든다
  (`common` = 가운데 한 덩이, `divergent` = 좌우 한 쌍)
- 조각마다 `"<행번호>:<순번>"` 형태의 안정적인 id 가 있다. 편집 상태(채택한 쪽,
  손으로 고친 문장)를 이 id 에 매달면 렌더링을 건드리지 않고 얹을 수 있다
- `commonTextOf()` 가 이미 "가운데만 이어 붙인 본문" 을 돌려준다. 편집 결과를
  내보낼 때의 출발점이다
- 갈림 조각에 "왼쪽 채택 / 오른쪽 채택 / 직접 입력" 을 붙이면 병합 편집기가 된다.
  그때 편집 상태를 store 에 둘지(되돌리기·내보내기까지 생각하면 그쪽) 정한다

## 3. 알려진 한계 (사용자에게 설명해야 하는 것)

기획서 §5.6 과 각 파서의 한계를 합친 것. `/docdiff/admin` 에도 같은 내용이 있다.

- **색 강조 토큰은 배경용이다.** 글자로 쓸 때는 `--color-add-text` /
  `--color-del-text` 를 쓴다. `*-strong` 을 글자색으로 쓰면 대비가 모자란다
- **문단 이동(move)을 감지하지 못한다.** 자리만 바뀐 문단은 삭제+추가로 보인다. v2
- **표는 평탄화된다.** 셀 단위 변경을 짚어주지 못한다
- **서식만 바뀐 변경은 잡지 않는다** (D-03). 볼드 추가 등
- **배포용(열람 제한) HWP 는 열 수 없다.** 감지해서 안내만 한다
- **스캔 PDF 는 비교를 차단한다.** 브라우저 OCR 은 100쪽에서 UX 가 무너진다
- **다단 조판 PDF 의 읽기 순서는 추정이다.** 신뢰도를 0.6 으로 낮춰 표시한다
- `.doc`(구버전 바이너리)는 지원하지 않는다. `.docx` 로 저장 후 재시도 안내

### 이 프로젝트에서 이미 밟은 지뢰

같은 실수를 반복하지 않도록 남긴다.

1. **워커에는 DOM 이 없다.** 기획서의 `DOMParser`·mammoth 예시를 그대로 쓰면
   배포에서 죽는다. `core/xml.ts` 스캐너를 쓴다
2. **프록시가 `/docdiff` prefix 를 뗀다.** 빌드는 절대경로, 서빙은 루트.
   상대경로로 두면 끝 슬래시 없는 주소에서 자산이 다른 앱으로 새어 나가고,
   서빙까지 절대경로로 두면 무한 리디렉트가 된다
3. **플랫폼은 `vite preview` 로만 띄우고 재빌드해 주지 않는다.**
   `rebuild-if-stale` 플러그인이 그걸 메운다
4. **O(n·m) DP 는 블록 8,000개에서 256MB 를 잡는다.** Myers + 앵커 분할로 바꿨다
5. **Comlink 는 Error 서브클래스를 message/name/stack 으로만 넘긴다.** 워커에서
   AppError 를 그대로 던지면 `code` 가 사라진다. `toJSON()` 으로 바꿔 던진다
6. **워커를 terminate 해도 이미 큐에 올라온 메시지는 배달된다.** 취소 뒤 도착한
   진행률을 그대로 반영하면 화면에 진행률이 되살아난다
7. **Tailwind v4 는 `@theme` 을 전부 `:root` 하나로 끌어올린다.** 미디어쿼리 안에
   `@theme` 을 두면 미디어쿼리가 사라지고 뒤 값이 앞 값을 덮어쓴다. 테마 오버라이드는
   평범한 `:root` 규칙으로 쓴다
8. **테마 검사는 팔레트가 정말 바뀌었는지부터 확인한다.** 안 그러면 같은 화면을
   두 번 보고 통과했다고 적게 된다
